## Receipt and trust boundary

Use an owned, closed, bounded JSON receipt, schema`earthship-native-model-verification-receipt/v1`, written only after the existing full`read_native_candidate` numerical validator succeeds under the production interpreter and the existing guards. Retain:

- Verification time and validator/source-profile identity.
- Candidate artifact and runtime identities, canonical artifact digest and exact candidate file SHA256.
- The exact four original paths, byte digests and declared size bounds.
- Interpreter/dependency binding and complete executing source closure, including the new serving helper.
- The independently checked fit identity, sensor epochs, numerical model rule and the immutable candidate identity; confidence remains low and release authorization false.

The receipt is evidence of deployment admission. It is not a new model, fit or forecast. Persist it atomically as0600 in an owned0700 directory, without replacing another receipt. Its digest and path must be pinned by the qualified final stage and the owned effective service selection; untrusted inputs cannot supply or renew the expected digest. No new signing credential or database table is required. The account authorized to replace the owned deployment configuration remains the existing configuration trust boundary; this is not a defense against that account deliberately replacing its own approved selection.

Avoid a circular binding: the receipt binds the source closure, runtime, candidate and original evidence, not the final deployment-record digest. The final deployment record includes the receipt's external digest and configuration; the effective service selection pins that completed deployment with an explicit external deployment digest. The serving reader must receive those pins from the owned qualified selection, never from an HTTP payload or a receipt's self-reported digest. A mutable receipt cannot authorize itself through its own content hash.

## Admission and serving flow

1. Commit the serving code, construct its runtime-bound candidate from the retained original fit, and stage the exact sources. Preserve all72 fitted sources and nine REQUIRED native fitting sources. Bind the new helper transitively through literal source pins in the OPTIONAL native serving modules and through the stage manifest, following the existing resource-helper pattern; do not change the fitted artifact validator.
2. With the original shared lock and headroom guards, perform full candidate replay once with the production interpreter. Read all original dependencies and the runtime before and after validation. If any binding changes, refuse receipt creation. Write the immutable receipt only after success; perform bounded exact readback without invoking another fit. Source and receipt creation remain private until activation admission succeeds.
3. Form the final stage/configuration and coherent forecast/preparer/scorer family with the externally pinned receipt. Introduce an explicit live configuration profile rather than silently changing existing v2 behavior. Existing v2 callers retain full validation; receipt serving is explicit and source-bound.
4. At the start of each admitted cycle, re-read complete candidate and original evidence bytes with the existing bounds and file protections. Recompute runtime/source bindings and compare every digest with the externally pinned receipt. Verify required chronology and cheap schema/coefficient/physical-bound checks. Return an immutable, opaque serving-model object only from this reader. Constructors, caller dictionaries and receipt fields cannot independently mint that object.
5. Use that object in explicit serving entry points for geometry preparation, capture construction and native scoring. Existing public/offline`build_capture`, `validate_capture`, `read_native_candidate` and score/replay entry points keep their full independent validation behavior. Share the unchanged numerical recurrence and trajectory checks; do not introduce a second model equation or a permissive fallback.
6. Before publishing, recheck exact selected bytes/runtime, shared-lock ownership, current source freshness and the original causal/deadline guards. During a cycle retain the frozen validated object; if the selection changes, withhold that cycle and require new admission. A missing, expired-by-chronology, malformed or mismatched receipt never falls back to a different candidate or regenerates itself inside a serving deadline.

All source metadata and dependency digests are read again for each cycle. Across numerical steps retain current kernel/resource/pressure checks and the existing source-drift observer. Reuse only the result of numerical candidate validation, not prior availability or hardware telemetry.

A new fit or source/runtime revision requires a new candidate binding and a newly issued verification receipt. Retain the old receipt for original forecast/outcome replay. Late outcome scoring must use the capture's externally pinned model selection and retained source archive, not today's selected receipt; if its retained receipt/dependencies are unavailable, qualify no score. Independent offline replay remains available through the full validator. Existing legacy v1 outcome queues are preserved; native selection must not silently abandon their pending jobs. An explicit historical full-replay mode may use its original pins, but a failed receipt read cannot silently select that mode or another model.

## Spec self-review

No source/runtime/config/receipt digest cycle is introduced: final deployment identity is outside the receipt and pinned by the effective service selection. No receipt issues its own trust pin, no untrusted request selects a receipt, and same-account deployment administration remains the existing explicit trust boundary. The four original evidence files and executing source closure remain required. Original replay APIs stay independent; historical selections and legacy outcome queues are retained. Current input freshness, pressure guards and physical authority stay separate from candidate verification reuse. This is one serving-admission change, not an automatic training/promotion service or a household-control rewrite. Implementation begins only after written-spec and implementation-plan review.
