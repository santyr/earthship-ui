# Production weather sensitivity

The explicit `weather-sensitivity.service` sidecar generates the three cases declared in `scenario-protocol.json`: central, half solar, and +3 C with 1.2 times solar. It reads the latest completed household energy/plan originals and the verified native deployment and interpreter. It never queries the cloud or observation database, trains a model, changes the household selector, or operates equipment. The installed timer runs at minute 18, away from the five-minute household issue boundary. An origin more than 15 minutes old is withheld. The worker is disabled unless explicitly enabled, and publication additionally requires `--publish`.

The Earthship page shows the confirmed cases in a collapsed Weather sensitivity detail. PV is component physics **before electrical correction**; the selected calibrated central PV forecast remains a separate product. Storage holds current qualified AC load, nominal bank capacity and original initial state fixed. Thermal projections retain the actual fitted thermal model and selected production temperature points. The declared temperature perturbation ramps from the unchanged initial observation to the first future point. Actions and all model coefficients remain fixed.

These constructed cases have no probabilities, measured usable-capacity claim or physical qualification. Joint scenarios remain `insufficient_evidence`: there is no complete qualified physical-GHI/joint measurement contract or eight eligible template dates. The production entry point accepts no residual templates and uses a named unavailable-target-cohort identity, separate from eligible physical target cohorts. Deterministic cases do not wait for joint probability qualification.

## Storage, confirmation and replay

`scenario-reports` is part of the existing shared 2 GiB/10,000-object state budget. Optional sensitivity objects have a separate 256 MiB ceiling and leave 384 MiB of shared capacity for core work. Disk reserve remains 32 MiB. Failure leaves original clocks intact and does not disable core publishers. No history is evicted. A single actual issue measured 175,591 retained bytes plus 3,736,880 source-generation bytes, or about 122 MB for 28 days hourly with one generation. These are measurements, not allowances; per-write checks continue to apply.

Compact originals retain gzip source-package chunks once per generation and byte-pinned references to the original private energy/plan files in the native stage. Keep those stages and all parent files. `restore_compact(state, report_sha256)` verifies every reference and reconstructs the exact original canonical bytes, including the original source packages. `scenario_reporting.replay_report` then verifies the retained numerical producer and outputs. Replaying an older original requires its original adapter source root and binary environment; changing a pointer to a new source tree is not replay.

An immutable opportunity record binds each original household pair, producer, policy and adapter runtime before the public cache is written. A retry reuses its first generated/expiry clocks. Publication confirms the literal cache bytes after readback; `/api/weather-sensitivity` serves only an owned private cache with its matching immutable confirmation. GET never reconstructs an original or executes a model. Missing, expired, malformed or unconfirmed reports produce explicit unavailability.

## Installation and rollback

Prepare a private `~/.config/earthship-weather/scenarios.env` containing `EARTHSHIP_SCENARIO_ROOT`, `EARTHSHIP_SCENARIO_PYTHON`, `EARTHSHIP_SCENARIO_STATE`, `EARTHSHIP_SCENARIO_OBSERVATION` and `PYTHONPATH`. Pin a permanent reviewed source root and supported interpreter. `PYTHONPATH` must contain that root's `openhab/scripts` and the pinned companion library. Install the two deploy unit templates only after tests, review, normal required CI, private actual-input preview, cache confirmation and browser checks pass.

Rollback disables/stops the new timer/service and restores the preceding UI unit override. It does not restore or refit any active model, change the collector, delete originals, or rewrite scores. Preserve the source root, interpreter, source chunks, private parents, opportunity records and confirmations for replay. Existing native, scalar, calibrated household and evaluation roles retain their separate source pins.
